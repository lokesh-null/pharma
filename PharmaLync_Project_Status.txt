1. WHAT IS PHARMALYNC?
================================================================================

PharmaLync is a comprehensive, secure healthcare platform that connects
Patients, Doctors, Pharmacists, and Administrators through a unified web
application. It integrates a backend API with a modern React frontend and
Ethereum blockchain smart contracts.

The platform is designed to:
- Securely manage patient medical data using multi-layer encryption
- Provide consent-based access to sensitive data (e.g., Aadhaar numbers)
- Maintain immutable audit trails on both a local database and the blockchain
- Prevent double-dispensing of medicines via blockchain verification
- Support role-based dashboards (Patient, Doctor, Pharmacist, Admin)
- Use Email OTP-based passwordless authentication

It is an Indian healthcare context application, built with compliance in mind
for UIDAI (Aadhaar regulations), DPDP Act, and HIPAA-like standards.

5. AUTHENTICATION SYSTEM (Email OTP-Based)
================================================================================

The authentication flow is OTP-based (passwordless primary, with optional password).

SIGNUP FLOW:
1. User submits email, fullName, phone, dateOfBirth, gender, role via POST /api/auth/register
2. Backend creates User record (isVerified=false, passwordCreated=false)
3. Backend generates 6-digit OTP (crypto.randomInt), hashes with SHA-256, stores in Otp table
4. OTP is sent via email (Nodemailer SMTP or logged to console in dev)
5. User enters OTP on frontend -> POST /api/auth/verify-otp
6. Backend verifies OTP using constant-time comparison (crypto.timingSafeEqual)
7. On success: generates JWT access token (15min) + refresh token (7 days)
8. User is redirected to /create-password page
9. User creates password -> POST /api/auth/create-password
10. Password is hashed with bcrypt (10 rounds) and stored

LOGIN FLOW:
1. User enters email + password -> POST /api/auth/login
2. Backend verifies password with bcrypt.compare
3. On success: generates JWT token pair (access + refresh)
4. Frontend stores tokens in localStorage, user in Zustand (persisted)

TOKEN REFRESH:
1. When access token expires (401 response)
2. API client automatically calls POST /api/auth/refresh with refresh token
3. New access token is returned and stored
4. Original request is retried transparently

OTP SECURITY:
- 6-digit cryptographically secure OTP (crypto.randomInt)
- OTPs are SHA-256 hashed before storage (raw OTP never persisted)
- 5-minute expiration
- Max 5 verification attempts per OTP
- Max 5 OTP generations per user per 15-minute window
- 30-second cooldown between resend requests
- Used OTPs are immediately invalidated
- Constant-time comparison to prevent timing attacks

JWT TOKEN DETAILS:
- Access Token: 15 min expiry, HS256 algorithm, issuer "pharmalync", audience "pharmalync-api"
- Refresh Token: 7 day expiry, HS256 algorithm, same issuer/audience
- Consent Token: 60 min expiry, HS256 algorithm, issuer "pharmalync", audience "pharmalync-consent"
- Each type uses a separate secret (JWT_ACCESS_SECRET, JWT_REFRESH_SECRET, CONSENT_TOKEN_SECRET)


6. SECURITY & ENCRYPTION DETAILS
================================================================================

--- THREE-LAYER AADHAAR PROTECTION ---
Layer 1 (Tokenization): HMAC-SHA256 with master key converts 12-digit Aadhaar into a
         deterministic 32-char hex token. This is a one-way operation.
Layer 2 (Encryption):   AES-256-GCM encrypts the token with random 16-byte IV.
         Storage format: [IV(16 bytes) | AuthTag(16 bytes) | Ciphertext]
Layer 3 (Hashing):      SHA-256 hash of the token (not raw Aadhaar) for database lookups.
         Verification uses crypto.timingSafeEqual for constant-time comparison.

--- PII ENCRYPTION (names, DOB, phone, address) ---
- Algorithm: AES-256-GCM
- Key derivation: HKDF-SHA256 per user (derived from master key + userId salt)
- Random 16-byte IV per encryption
- Auth tag verification on decryption
- Storage format: [IV(16) | AuthTag(16) | Ciphertext]
- Bulk encrypt/decrypt support for multiple fields

--- KEY MANAGEMENT SERVICE (KMS) ---
- Master key: 256-bit (64 hex chars from ENCRYPTION_KEY env var)
- Validates key format on startup (must be 64 hex characters)
- Per-user key derivation using HKDF-SHA256 (Extract + Expand)
- Key rotation placeholder for AWS KMS / Azure Key Vault integration
- Required env vars validated on startup: ENCRYPTION_KEY, JWT_ACCESS_SECRET,
  JWT_REFRESH_SECRET, CONSENT_TOKEN_SECRET

--- QR CODE SECURITY ---
- Authenticated Encryption: AES-256-GCM with derived key per resource type
- Digital Signatures: HMAC-SHA512 over (IV + Tag + Ciphertext)
- Anti-replay: Random 16-byte nonce + timestamp embedded in payload
- Key derivation: HMAC-SHA256 from master key with context strings
  (QR_TOKEN_{type} for encryption, QR_SIGN_{type} for signing)
- Format: base64url(JSON{ iv, tag, encrypted, signature })
- Verification: Signature checked BEFORE decryption (sign-then-encrypt model)
- Constant-time signature comparison to prevent timing attacks
- Public lookup hashes: HMAC-SHA256 for blockchain ID obfuscation

--- PASSWORD SECURITY ---
- Hashing: bcrypt with 10 salt rounds
- Password comparison: bcrypt.compare (constant-time)
- Seed script uses PBKDF2-SHA512 with 10,000 iterations, 16-byte salt, 64-byte output

--- INPUT SANITIZATION ---
- Strips <script> tags and all HTML tags from all input
- Applied recursively to request body and query params
- Runs as global Express middleware on every request

--- HTTP SECURITY HEADERS (Helmet) ---
- Content-Security-Policy: self-only scripts/styles, data: and https: for images
- HSTS: max-age 1 year, includeSubDomains, preload
- X-Frame-Options: DENY
- X-Content-Type-Options: nosniff
- XSS Protection filter enabled

--- CORS ---
- Configurable allowed origins (default: localhost:5173, localhost:3000)
- Credentials: true
- Methods: GET, POST, PUT, DELETE, PATCH
- Custom headers allowed: Content-Type, Authorization, X-Consent-Token

--- RATE LIMITING ---
- Global: 100 requests per 15-minute window per IP
- Auth endpoints: 10 requests per 15-minute window per IP (stricter)
- Returns 429 with JSON error message


7. CONSENT MANAGEMENT SYSTEM
================================================================================

Consent is managed through time-bound, scope-limited JWT tokens.

CONSENT SCOPES:
- VIEW_MEDICAL_RECORDS: Permission to view patient medical records
- VIEW_AADHAAR: Permission to view decrypted Aadhaar number
- UPDATE_RECORDS: Permission to update patient records

FLOW:
1. Patient grants consent -> POST /api/consent/grant
2. Backend creates Consent record in DB + generates JWT consent token
3. Token contains: consentId, patientId, grantedTo (userId), scopes, expiresAt
4. Doctor/Pharmacist includes consent token in X-Consent-Token header
5. Middleware verifies: JWT signature, expiry, scope match, revocation status
6. Patient can revoke consent anytime -> POST /api/consent/revoke

TWO VERIFICATION MODES:
1. Token-based: Via X-Consent-Token header (for explicit consent flows)
2. Database-based: Direct DB check for active non-revoked consent (for implicit flows)


8. AUDIT LOGGING SYSTEM (TWO-TIER)
================================================================================

TIER 1 — LOCAL DATABASE:
- All actions logged to AuditLog table
- Fields: userId, action, resourceType, resourceId, metadata (method, path, IP, userAgent)
- Indexed queries with filtering by user, action, resource, date range
- Automatic logging via Express middleware (logs on successful 2xx responses)
- Two modes: "after response" (auditLog) and "before action" (auditLogBefore)

TIER 2 — BLOCKCHAIN:
- Critical actions automatically logged to Ethereum (Sepolia) via PharmaLyncAudit contract
- Critical actions: VIEW_AADHAAR, CREATE_PATIENT, UPDATE_PATIENT, MEDICINE_DISPENSE, PRESCRIPTION_CREATE
- Only SHA-256 hash of audit data is stored on-chain (NO PII ever goes to blockchain)
- Transaction hash stored in local AuditLog.blockchainTxHash field
- Blockchain logging is async and non-blocking (failures don't break operations)

INTEGRITY VERIFICATION:
- Admin can verify any audit log against blockchain via GET /api/audit/verify/:id
- System recalculates local hash and compares with on-chain hash
- Returns: valid (bool), localHash, blockchainHash, error message if mismatch
